# 个性化美术资产与动画流水线

本文记录玩家输入如何变成梦境中的模型，以及房间色彩、统一美术方向、Tripo 生成、绑定、动画和失败回退之间的关系。它是设计与接入方案，不代表 API、资产或动画已经实现或验收。

## 1 体验目标

玩家在开始游戏前分别填写喜欢与害怕的事物，例如“喜欢：玩偶；害怕：蛇”。游戏将输入转成可控的场面方案，按房间主题生成或载入对应模型，再把模型放进房间并驱动相应行为。

核心链路：

```text
玩家输入
  → 语义归一与玩家确认
  → 兼容剧本／行为方案
  → 房间色彩与统一美术描述
  → Tripo 文本生成任务
  → 结果检查与本地保存
  → 可选绑定与动画任务
  → Three.js 加载、摆放与行为驱动
```

模型生成外观；游戏的确定性规则控制位置、观察、回访、追逐、碰撞和状态。模型服务不得决定或执行游戏代码。

## 2 输入与语义方案

- 输入界面分别询问“你喜欢什么”和“你害怕什么”，避免仅有一串词时无法判断其叙事角色。
- 保留玩家原词供确认与叙事使用；语义层另生成规范物件名、类别、角色、兼容剧本、资产描述及房间引用。
- 喜欢和害怕是不同角色。同一个“玩偶”可以是喜爱物，也可以是恐惧物，不能只由物件名称决定演出。
- 语义层只从已登记的剧本、行为、空间和动画类别中选择。未知词可以作为 Tripo 的物件主体继续尝试；若无法确定安全、可实现的场面，则请求玩家修正或提供预设，不杜撰游戏机制。
- 结构化结果须经字段、长度、枚举、空间引用及前置事实校验。禁止执行模型返回的代码或未登记行为。

建议的中间数据：

```json
{
  "input": { "like": "玩偶", "fear": "蛇" },
  "assets": [
    {
      "subject": "布偶",
      "role": "favorite",
      "script": "return_visit_change",
      "roomId": "bedroom_01",
      "bodyPlan": "biped"
    },
    {
      "subject": "蛇",
      "role": "fear",
      "script": "lurking_threat",
      "roomId": "bedroom_02",
      "bodyPlan": "serpentine"
    }
  ]
}
```

字段名仅为设计示例；接入运行时前应与剧本卡和稳定 ID 对齐。

## 3 房间主题色与统一美术方向

### 每个房间定义自己的颜色

房间配置提供色盘和灯光参数，不能把所有生成物固定为脏黄绿与紫黑。模型提示词引用其所属房间的主色、辅助色、材质和光照；Three.js 房间灯光、雾和后处理同时引用同一主题配置。

```js
const roomTheme = {
  palette: ['#7589a6', '#c2c7c8', '#4a566a'],
  materialMood: '褪色布料、粉化墙漆、哑光旧木',
  keyLight: '#9bb5d2',
  shadowColor: '#242638',
};
```

这组值是配置格式示例，不是最终色彩标准。实际房间可使用冷蓝、暖粉、灰白、青绿等不同主题。若纹理颜色和灯光冲突，应先检查纹理输出及材质色彩空间；只有无纹理或已验证的材质才直接用运行时颜色染色。

### 全游戏共享的造型规则

每个房间可换颜色，模型仍应看起来属于同一款游戏。共享的造型描述方向为：

- 低模低清、略粗糙的独立游戏 3D 质感；不追求写实皮肤或精致电影级渲染。
- 物件仍须容易辨认，再对比例、关节、朝向、表情或影子做一两处不协调的改变。
- 不对所有输入套用同一张脸、眼睛或怪物模板。猫、玩偶、蛇、花、音乐应保留各自的形态和表达方式。
- 不稳定视角、过度僵直、错位结构、重复形状和不可能的姿势可用于梦境失序感；不要把现实精神疾病当作美术规则或角色解释。
- 不用过暗或过多噪点掩盖出口、可交互物和威胁提示；场景的色彩差异不能损害可读性。

### 提示词组成

提示词由固定风格、玩家物件、场面角色、房间配置和模型约束组成：

```text
固定风格 + 物件主体 + 喜爱／恐惧角色表达 + 房间主题色与材质
+ 单物件／完整轮廓／比例和朝向要求 + 排除项
```

例如“猫 + 冷蓝卧室”应继续是一只可辨认的猫，整体采用灰蓝、冷白的房间色彩；不应因全局风格而自动变成黄绿色，也不应被改造成通用人形怪物。玩家输入决定“是什么”，房间配置决定“用什么颜色和材质”，剧本决定“它怎样异常”。

## 4 Tripo 接入与资产落地

- 当前 Tripo 文本转模型使用异步任务：后端创建任务并记录 task ID，之后查询终态，再取回模型文件。浏览器不直接持有服务密钥。
- 提交给生成服务的内容仅包含当前任务需要的物件描述与房间色彩，不发送完整玩家偏好档案。
- 生成任务、模型下载和动画任务分别记录供应商版本、参数、任务 ID、资产摘要与终态。超时不能视为任务失败，也不能据此盲目重复创建收费任务。
- 模型下载链接是临时地址。任务成功后应尽快下载并保存可由游戏读取的 GLB；恢复会话时先查询既有任务，不重复创建。
- 模型加载前检查真实格式、文件大小、包围盒、比例、朝向、材质和外部资源引用；归一化比例与落地原点后才加入房间。
- 每局先限制为最多两项动态生成任务，优先验证一项。模型任务、纹理任务和动画任务的额度及等待时间都需用实际账号实测。

### Tripo API 任务顺序

按当前官方 v2 OpenAPI 说明，文本生成和后处理都通过 `POST /v2/openapi/task` 创建异步任务，再通过 `GET /v2/openapi/task/{task_id}` 查询。典型顺序为：

```text
text_to_model
  → 检查是否可绑定（animate_prerigcheck）
  → animate_rig（按身体结构选 biped／quadruped／serpentine 等）
  → animate_retarget（选择该绑定版本实际支持的动画）
  → 下载动画 GLB 并在 Three.js 验收
```

官方 Schema 当前列出 `preset:quadruped:walk` 与 `preset:serpentine:march` 等预设；这不等于存在满足本项目的自定义“爬行／蠕动”片段。最终动作要实际检查，不符合追逐效果时由游戏根节点移动或经单独制作的程序动画补足。不同 API 版本、绑定模型版本和动画预设可能不同。

参考：[Tripo API 通用说明](https://platform.tripo3d.ai/docs/general)、[Tripo OpenAPI Schema](https://platform.tripo3d.ai/docs/schema)、[Tripo 绑定与动画参数（Schema）](https://platform.tripo3d.ai/docs/schema)。接入时锁定正在使用的官方版本；不得将产品网页端能力、不同 API 版本或 SDK 字段混用。

## 5 绑定、动画与向玩家移动

文字生成得到的静态模型不等于可动画资产。若要绑定，应将其作为生成之后的独立任务，并按经检查的身体结构选择绑定类型，例如四足或蛇形；不能仅凭玩家输入的词假设模型一定可绑定。

- 先检查模型是否可绑定，再创建绑定任务；绑定失败或骨骼结构不可用时进入明确回退。
- 适配到位移动画后，优先使用原地循环，再由游戏控制模型根节点朝玩家移动。动画循环负责四肢或身体动作，根节点负责世界空间位移与停止距离。
- 四足行走、蛇形蠕动等动画应按类别单独预览。若内置动作不符合“爬行”，不能把步行动作直接标成已验收的蠕动动画。
- 对外观有用但骨骼不可用的资产，可退回简化的根节点靠近、贴地俯仰、身体轻微起伏和头部摆动。该回退只能表达临时演示效果，不可冒称完整骨骼动画。
- 动画更新仅在场景活动且未暂停时推进；暂停冻结动画和追逐计时。离屏追逐需要继续更新持久位置，房间重新加载后恢复一致状态。
- 动态资产替换不得改变碰撞体、威胁规则或玩家反制方法。必要时使用稳定的独立碰撞体包围盒，不以生成网格直接决定通行状态。

### 运行时驱动概念

Three.js 使用 `GLTFLoader` 加载模型。若 GLB 含已验证的动画片段，用 `AnimationMixer` 播放；每帧再由追逐状态更新根节点位置。运行时应确认动画片段存在、绑定名匹配、模型朝向正确、到达玩家前会停止，并可在暂停、死亡和房间卸载时正确停止或恢复。

伪代码：

```js
if (gltf.animations.length > 0) {
  mixer = new THREE.AnimationMixer(model);
  mixer.clipAction(gltf.animations[0]).play();
}

// 在有效追逐状态时更新根节点；动画片段本身可保持原地循环。
moveRootTowardPlayer(model, player, speed, stopDistance, deltaTime);
```

此段只描述职责划分，不是已接入的项目代码，也不指定最终速度或停止距离。

## 6 演示、超时与回退

- 玩家输入完成后显示生成阶段；模型尚未可用时不锁死游戏，也不允许把未知任务状态当作成功。
- 模型成功后，如绑定／动画仍处理中，可先载入静态模型，并使用已验收的根节点运动回退。
- 超时、额度不足、API 错误、无效 GLB、绑定失败或动画片段缺失时，使用本地占位模型／程序化几何完成场面。
- 提交前缓存可演示的 GLB 和动画，现场网络异常时可以重复完成试玩；缓存资产应记录来源和生成参数。
- 演示必须分别展示玩家输入、实际生成模型和游戏内行为。截图或模型预览不能替代可试玩的加载与动画链路。

## 7 验收项

| 环节 | 通过条件 |
|---|---|
| 任意支持词输入 | 新物件不要求为每个名词增加硬编码模型分支；无法编排的输入有明确确认或回退 |
| 房间色彩 | 同一物件在不同房间采用相应主题描述与灯光；模型仍保持全局造型规则 |
| 识别度 | 玩家能辨认输入物件；异常设计没有抹掉主要轮廓 |
| Tripo 任务恢复 | 任务 ID 可查询；超时不会重复扣费创建；模型下载并保存后可从本地加载 |
| 模型接入 | GLB 比例、朝向、材质和落点正确；出口、家具、碰撞和威胁规则不受模型替换影响 |
| 绑定和动画 | 绑定类别匹配身体结构；目标动画片段确实播放；模型能朝玩家移动并按规则停止 |
| 失败回退 | 生成、下载或绑定失败仍可继续试玩，界面明确状态 |
| 暂停与死亡 | 暂停时动画和追逐计时冻结；死亡后按剧本规则重置临时行为并保留永久状态 |

测试记录必须区分“设计完成、接口实现、任务成功、GLB 加载、绑定成功、动画验收、真人试玩”。不得用其中一项代替其余项目。
