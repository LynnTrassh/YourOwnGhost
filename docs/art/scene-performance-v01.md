关闭阴影、绕过 VHS 都改变着色器变体和渲染目标；这些条件自身也首次生成程序，出现秒级停顿。不能直接用它们的最长帧比较效果优劣，或声称关掉阴影即可解决卡顿。顺序、驱动缓存和后台负载同样影响对照；固定灯光组还跳过了 world.update，因此不是仅修改灯光单变量的修复验证。

本路径完整效果绘制数中位数 279，约 15.3 万三角面（包含多 pass）；关闭阴影约 161 次、6.8 万三角面。其他任务历史视角的约 1111 次绘制不应套用到本路线。

## 代码对应原因与后续接入顺序

### 第二轮着色器归因

原始文件：[results-shader-trace.json](../../art-source/scene-performance-v01/results-shader-trace.json)。重新载入诊断页，在其独立 WebGL context 包装 compileShader、linkProgram、getProgramInfoLog、getShaderInfoLog、getProgramParameter、getShaderParameter、getActiveUniform、getUniformLocation，累计这些 API 的墙钟耗时，不调用额外同步 GPU 查询。

| 完整效果测量帧 | 渲染提交 | 着色器相关 API | 新程序/链接次数 | 可见室内灯 |
|---|---:|---:|---:|---|
| 27 | 208.1ms | 138.2ms | 5/5 | 2 个 SpotLight + 1 个 PointLight |
| 91 | 346.1ms | 304.0ms | 5/5 | 3 个 SpotLight |

第 91 帧约 88% 的渲染提交时间位于着色器相关 API 内。固定灯光组与最后重复完整效果均无新程序/链接事件，最长帧间隔 17.7ms。两轮停顿幅度不同符合驱动缓存/整机负载变化，但触发帧 27、91 重合，支持灯光变体首次准备是这段路径的主要卡顿来源。未覆盖全部房间和完整剧情，不排除其他位置另有瓶颈。

### 接入建议

1. `src/art/interior-lighting.js` 的 `update` 会改变 `light.visible`。跨房间时可见 SpotLight/PointLight 数量会变化。当前 Three.js 的 `WebGLPrograms.js` 明确将灯数、阴影数纳入程序缓存键；新的组合需要新程序。`src/main.js` 目前没有 shader 预热步骤，也没有等待 `world.artReady` 才允许开始探索。这是优先定位/修复方向。
2. 灯光隐藏时立即释放阴影贴图，再显示时重新分配。有限缓存或固定数量灯光槽可减少抖动，但本次重复路径证明分配本身不是每次都会产生长帧。固定灯光槽须保留房间优先级、事件光色和原本明暗，不能通过常亮所有灯掩盖问题。
3. `src/main.js` 暂停、blur、hidden 仅暂停玩法；动画回调末尾仍无条件调用 `world.renderScreens` 和 `vhs.render`。可在暂停/隐藏时停止或按需渲染，恢复时重置计时。主入口由程序方接入。
4. `art-source/room-detail-quality/preview.html`、`art-source/flashlight-contour/index.html` 持续刷新；模型预览虽跳过 hidden，仍在静止可见时连续绘制。适合改成输入/加载/动画变化才重绘；其他聊天仍拥有这些页面。
5. 之后再测全房间绘制预算、整体房间遮挡剔除与静态阴影缓存。禁止直接冻结正式游戏所有阴影：门、人物和事件会运动。

优先做首次进入前资源就绪与灯光着色器预热/稳定槽位，再处理暂停渲染；不需要首先删除家具或削弱已确认的光圈。
