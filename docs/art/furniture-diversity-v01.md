## 已核实原因

1. `src/art/interior-catalog.js` 有 36 个运行资产条目，其中 25 个映射到家具 prefab；每个 prefab 只有一个模型。床、沙发、衣柜、餐椅、书桌都无款式池。V02 与 V03 是版本/贴图优化，不是两种款式；旧 bed-v1 文件也不在当前床映射里。
2. `PREFAB_ASSETS` 用 `Object.fromEntries` 建一对一映射。直接添加三个相同 `prefabId: bed` 的条目会互相覆盖，最终仍只有一款；必须有明确的变体选择接口。
3. 最终家具补全目标为 `min(12,max(6,ceil(area/22)))`，候选锚点沿外围墙面。即使家具件数达标，125–225 m² 大房仍有大片没有中景层次的地面；加墙画不改变地面体积。
4. 主题只有六类，每类三个固定功能组；书柜、书桌和同一把餐椅跨主题复用。件数增长经常是同款复制，并不代表用途/轮廓增加。
5. 固定出生房被明确排除新增布置。床本身不会随机换款。加载阶段按 `asset.height` 和 `obstacle.height` 取较小值，新高柱床若直接复用低床槽会被压矮，损失主要特征。

## 布局接入提案：需要明确交接共享文件

按根目录 AGENTS.md，规划文件默认由程序方维护。本轮仅把修改方案做具体，没有跨任务接管。

建议范围：`src/planning/room-presets.js`、`src/planning/interiors.js`、`src/art/interior-catalog.js`、`src/art/dark-interiors.js` 及必要测试；不改地图拓扑、出生房或故事状态。若启用新字段需要 schema/校验调整，先核对接口再扩范围。

1. 从“沿墙几组＋总件数”改为显式区域：入口可识别组、主功能组、侧翼组、中部过渡组。普通大房先试 4–6 个功能组作为 A/B 候选，数量不是硬塞门槛。低家具可放侧翼内区，高家具避开已声明观察线；不动门口通行、事件锚点与碰撞安全规则。受保护动态房保留专用策略。
2. 为六类房间制定可识别的主物件组合，不再让通用柜桌成为所有房间的主体。每次检查整组关系：卧室床/梳妆/衣物；客厅会客/展示；育儿室矮桌/玩具/照护；诊疗室检查/器械；档案室阅档/存档；供奉室供桌/等待。后续优先补屏风、衣帽架、洗漱架、摇椅、旅行箱等轮廓缺口，避免继续堆近似方柜。
3. 建立独立 `variantId` 或等效确定性字段。规划时用独立美术种子选型并保存；同层普通卧室主床尽量不重复相邻款，固定出生房锁定原床。渲染只解析已选变体，不在加载时随机。只更改一对一 catalog 无法实现此功能。
4. 低床变体可共享经过验证的物理槽；四柱床属于高度/遮挡不同的独立方案，保持实际比例并单独校验。不得把 2.2 m 高柱床压成 1.05 m 来满足旧槽。
5. 验收增加三项：每房主用途是否一眼读出；入口/中部/回望是否至少能读到相互不同的物件组；同款重复是否是有意的规律。唯一模型数与占地率用于发现异常，不代替构图评审，不把极端恐怖重复房判成错误。

预期 A/B：125 m² 客厅从当前两组沿墙摆设扩为主会客区、侧翼阅读区、展示区与过渡小组；控制组保留当前结果，同种子同视角比较。验证最终 generateDream 的事件数据/导航/碰撞/幂等和种子确定性，执行 npm test、build，再做四视点实景。不通过约束时减少组或换锚点，不能删事件来腾位置。
