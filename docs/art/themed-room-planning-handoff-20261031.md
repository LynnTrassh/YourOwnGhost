## 先成立用途，再设计恐怖

| 主题 | 房间必须能读出的关系 | 当前草案需要纠正的代表问题 |
|---|---|---|
| 医院 | 候诊→接诊/检查→医疗储藏，医疗设备指向操作位 | 家用餐椅不够表达候诊；家用床加药柜不等于隔离病房 |
| 游乐场 | 售票/检票、实际游艺或演出、领奖与奖品、后台 | 领奖间必须有台体与观众朝向；八间全是普通后台会削弱主题 |
| 公司 | 接待与员工分区、成组工位、会议共同注视面、邮件/档案流转 | 文件桌不能通吃前台、会议和收发；收发室必须能看见分拣结构 |
| 个人住宅 | 睡眠、起居、阅读、吃饭、个人物件与储藏各有用途 | 带文件的工作桌不适合作餐桌；旧物间需要实际旧物，不只是更多柜子 |
| 旅馆 | 前台/钥匙、短住行李、客房、布草周转和公共等候 | 行李室不能用玩具箱和矮柜代替；布草间必须出现床单与周转设备 |
| 祭祀空间 | 供奉对象、供品/祭器、参与者朝向与仪式中心 | 两个空柜不是“双像”；红光不是祭祀用途本身 |

领奖间优先重新构图：建议从当前5×5米调整为10×10米候选，包含高台、侧阶、主持位、三级领奖位、面对台面的观众席和侧翼奖品。此建议改变房间占地，必须由规划方显式确认新布局，不能作为原房外观直接替换。

游乐场后续模型清单把街机配到“手工教室/员工室”、旋转木马配到“等候厅/奖品仓”。这些组合仍需策划判断用途：若主物件改成游艺设施，应重定义房间用途和动线；不能因为新模型生成了，就随意塞到原名字的房间里。

## 三层独立控制与候选模块

下列模块在本地候选目录，**不包含于本次资料提交**，收到单独代码交付后再接入。

| 层/模块 | 当前实现和验证范围 | 正式调用责任 |
|---|---|---|
| 空间：`ceiling-art.js` | 独立顶面绑定、默认关闭；顶面底高3米，装饰最低2.94米；静态绑定及资源释放专项检查通过 | 程序绑定实际顶板，动态房须随同根节点变换并重新验证 |
| 空间：`crimson-room.js` / `shrine-room-finish.js` | 显式材质/既有灯光绑定与还原；血色和材质来自空间，非全屏红滤镜 | 程序管理材质所有权、关闭恢复及释放顺序，避免污染邻房 |
| 摄影机：`low-light-camera.js` | 正常探索默认subtle；校准场景A–E、输出链和局部像素对照已做 | 与正式 `vhs-effect.js` 选择整合方式，恰好一次色彩输出转换；保持用户强度控制 |
| 信号：`recording-signal.js` | 无自动触发；显式区域、强度、秒数；30/60/120Hz时间与取消检查通过 | 策划在异常确实可见时调用；离开视野、暂停、换层、事件取消时取消或更新区域 |
| 遭遇插帧：`encounter-flash.js` | 独立鬼脸/黑影插帧资产候选，与房间布景和常驻噪声分开 | 事件侧负责触发、冷却与去重；不得在正常探索中随机反复闪屏 |
| 主题布局：`themed-room-library.js` / `themed-room-stage.js` | 48个确定性布局草案及独立录屏预览；技术加载/占地检查不是功能美术验收 | 先用真实新模型重新布景，再明确规划接口；不直接全量注册 |

信号接口约定：`trigger({id, region:[cx,cy,rx,ry], strength, duration})`，屏幕UV左下为原点；中心0–1、半径(0,.5]、时长.2–3秒、强度0–1。独立模块支持取消、区域更新和关闭，正在播放时不重入；可见性、遮挡判断、冷却与剧情条件仍归玩法侧。

原手电应继续采用正式构造角度与配置：`SpotLight`半角 `Math.PI/7`，再调用 `configureInteriorFlashlight`。仅调用后者不会设置角度，曾因此误用默认大光锥。当前候选预览最终值为强度24、距离17、penumbra .22、decay 1.65，并复用原cookie；接入时以正式配置为来源，不另造宽束效果。

## 尺度、朝向、导航与事件

- 建筑模块为5×5米，完整九宫格15×15米；当前地图导航格为5/3米，不能混用。
- 布局候选约定常规模型面向+Z；最新模型交接文档约定面向−Z。接入必须显式适配（通常旋转180°）并逐件观察正面，不能同时在源模型和布局各翻转一次。
- 用实测包围盒排布局。建议尺寸只是制作目标；不能压扁模型满足旧槽，也不能让台体、柜台、舞台高差悄悄改变可走区域。
- 家具、台面摆件、人物必须分别核实支撑面。旧供桌占地与事件灰盒不同，不能仅换模型路径造成供物悬空。
- 台阶需明确可走面和高度；当前独立预览主要为平面移动，不能据此证明正式台阶导航可用。
- 事件代理的根节点、观察目标、交互点、碰撞与动画绑定必须保留；终点睡姿人物等由模型任务交付后，需按真实床垫表面接触检查，不能直接替换终点逻辑。
- 房间构图/型号由规划阶段确定并保存；加载资源不得再随机布局或额外消耗原地图随机序列。新增美术变体字段需由规划方显式设计，保证旧种子仍可复现。

## 建议接入顺序与验收

1. 模型任务交付带来源、尺度、朝向、分件、材质与检查状态的资产；先核验领奖间P0，确认台阶是否仍缺。
2. 环境美术先重做领奖间，再各主题完成一间可识别用途的样板。去掉名称也能辨认功能，才扩到各八间。
3. 策划确定每间入口→主用途→异常发现→回望的过程，明确异常是静态布景、显隐变化还是事件逻辑，避免物件与机制相互解释不清。
4. 程序将确定性布局、碰撞和事件连接到正式地图；单独处理摄影机输出链、可见性判定及故障触发。
5. 每批验证：原种子复现/旧存档兼容（若涉及）、门洞和出口、导航与碰撞、事件目标和触发、切层/暂停/释放、原手电范围、明暗场景画质与目标设备性能。修改玩法/生成/碰撞运行项目测试；可运行接入运行构建，并在正式游戏中观察。

验收结果要分开记录：自动检查、构建、浏览器视觉观察、真人玩法。旧草案截图与校准GPU耗时不代表正式新房间通过。此次仅校验资料包的链接、JSON与交接一致性，没有新增游戏接入或玩法验收。
