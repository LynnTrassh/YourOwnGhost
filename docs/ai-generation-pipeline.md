# LLM 与生成式资产管线

版本：v0.1；日期：2026-10-30。依据 [GDD](game-design-v0.2.md)、[技术框架](technical-architecture.md) 与 [剧本总集](script-catalog.md)。本文定义项目内部协议与实施方案，不代表服务已接通或效果已验收。

## 1. 分工与边界

LLM 负责把玩家表达转换为可检查的素材语义，并从已制作的内容库中推荐匹配情节。确定性系统负责实际选择、空间、触发、状态、危险与通关。生成式模型负责符合资产规格的外观产物，不能替代动画与玩法实现。

| 能力 | 输入 | 输出 | 不负责 |
|---|---|---|---|
| 语义解释 | 玩家主动输入的喜欢／害怕内容、允许的语义标签 | 结构化解释、歧义、兼容素材特征 | 人格判断、诊断、虚构经历 |
| 内容推荐 | 玩家确认的解释、当前可用剧本能力目录 | 剧本排序、素材绑定建议与理由 | 任意新剧本代码、地图坐标、强制改变出口 |
| 资产描述 | 已选素材、风格与角色规格 | 形状、材质、尺度参考与生成提示词 | 玩家完整档案、系统密钥 |
| 3D 生成 | 最小化物体描述与输出规格 | 模型文件及任务信息 | 自动保证骨骼、死亡姿态、镜面或可用碰撞 |
| 游戏运行 | 已验证计划、真实事件 | 状态变化、固定台词与表现 | 逐帧调用 LLM、让模型决定玩家是否看见 |

首批旁白使用剧本总集中的固定文本和明确条件。真实语义服务与 3D 生成均属于完整制作范围；固定映射先验证接口，不作为最终 AI 能力的替代。语音制作优先离线录制或离线生成后审核入库，不在游戏中等待实时台词合成；实时改写旁白不纳入当前运行链。

## 2. 一局中的调用顺序

1. 输入页收集喜欢和害怕的事物，分别显示给玩家；限制文本长度，保留用户原句仅用于本次解释。
2. 客户端向项目服务端提交 interpretation 请求。正常路径调用 LLM 一次，返回解释、兼容素材标签与库内剧本建议。
3. 玩家确认或修改解释。修改后产生新 inputRevision；未确认不得创建收费资产任务。可直接选择已支持的解释，也可提交一次新的解释请求。
4. 确定性规划器校验候选、完成依赖闭包、选择剧本与空间计划。保存确认后的解释、计划、版本和 planHash。
5. 从计划中提取需生成的资产；先查已验证缓存，再创建至多两项生成任务。正常路径由确定性模板组装资产提示词，不额外调用 LLM。
6. 使用占位资产准备可玩场景。玩家可以选择继续等待或以明确标注的占位版开始；进入游戏不依赖生成成功。
7. 资产完成后校验并登记。已经进入演出的对象不在玩家眼前突然换外观；仅在尚未激活的实例、明确加载屏障或下一局绑定新资源。
8. 假醒、死亡、回访均复用已确认计划，不重新解释偏好、不重新创建资产任务。重开可以复用同一确认解释与资产缓存，但创建新的游戏 runId。

首次实现限制每个 inputRevision 一次正常解释请求、至多一次结构化纠错请求。输入修改属于新 revision，不是无限自动重试；服务端仍设置会话请求与费用上限。上限耗尽时给出明确反馈和已支持预设，不静默持续请求。

## 3. 内部请求与返回契约

以下字段是项目协议，不是任一供应商 API 的原生字段。服务适配器负责实际接口映射。

```json
{
  "schemaVersion": 1,
  "requestId": "interpret-001",
  "inputRevision": 1,
  "locale": "zh-CN",
  "likes": ["猫"],
  "fears": ["被东西盯着"],
  "catalogVersion": "content-v1"
}
```

解释结果示例：

```json
{
  "schemaVersion": 1,
  "inputRevision": 1,
  "interpretations": [
    {
      "inputRef": "likes[0]",
      "normalizedLabel": "猫",
      "semanticTags": ["animal", "cat", "group", "gaze"],
      "displayExplanation": "以猫群的凝视和回访变化构成场面。"
    }
  ],
  "ambiguities": [],
  "suggestions": [
    {"definitionId": "CAT01", "inputRef": "likes[0]", "reasonCode": "animal_group_gaze"}
  ]
}
```

完整 schema 使用固定字段、枚举、长度上限并禁止额外属性。建议结果只作为排序输入；必须再次检查 ID、素材兼容、实际可用能力、互斥、前置依赖与版本。未制作剧本可出现在全量设计库中，但不能进入当前可玩目录。模型返回“猫可以凝视”不证明对应资产已经支持头部转动。

拒绝未知 ID、非法引用、指令文本、脚本代码和越权字段。格式错误或枚举无效时允许一次纠错，仅提供具体校验错误；仍失败则使用明确标注的固定映射或让玩家修正。不要靠删除非法字段后猜测整份结果的含义。

## 4. 提示词结构与玩家修正

解释提示由四部分组成：固定职责与禁止事项、版本化语义标签、已可用剧本的精简能力摘要、作为数据传入的玩家文本。玩家文本与任何生成结果都不获得执行权限，不能覆盖固定规则。

内部提示模板表达以下约束：

> 将玩家主动填写的喜好与恐惧解释为本游戏可表现的素材。只选择给定目录中的编号与标签。遇到歧义列出可供玩家确认的解释，不猜测个人经历。只返回规定结构，不生成程序代码，不承诺尚未具备的表现能力。

输入“猫”可映射动物群体、注视、死亡或缺席；输入“花”映射密集摆放、枯萎；输入“音乐”映射重复、叠加与骤停。它们不能共用任意带眼睛的换皮策略。

解释页展示具体意思与将采用的素材，不提前揭示全部反转。玩家可修改原句、选择另一解释或接受明确的预设。PreferenceCorrectionConfirmed 仅在已确认解释实际发生变化后记录；第一次确认不等于修正。未确认解释不进入行为事实，也不能让旁白声称“我记得你改过”。

不支持的抽象输入给出具体可表现选项，选择权留给玩家。玩家拒绝所有选项时允许返回修改或退出，不把不支持输入悄悄替换成猫。

## 5. 从语义到可制作资产

AssetRecipe 在规划完成后生成，包含 recipeId、semanticBinding、用途、风格、targetSize、pivot、朝向、requiredCapabilities、状态变体、预算、fallbackAssetId。生成提示词由这些字段构造，而不是直接转发玩家整段文字。

以 CAT01 为例：

- 语义：猫、群体注视；实例复用同一套外观与有限变体，无需生成 24 个独立模型。
- 必需能力：头部可定向、活体姿态、倒地闭眼静止状态。声音来自音频资产清单。
- 静态整猫模型即使下载成功，也不自动满足这些能力。无法可靠拆分头部或制作死亡状态时，继续使用具备这些能力的制作资产。
- 真正替换前完成姿态适配、轮廓与穿插检查，并在活体／死亡两个阶段验收；不能为了使用生成模型而删去凝视和死亡表达。

花类可使用同一模型配材质／几何状态变体，但必须保留可辨认枯萎。BO02、BO04、AB04 需要专用结构、关节或形态动画；生成产物可作为外观制作材料，不能直接宣称支持拉长、弯曲和塌陷。镜面与监控由渲染系统实现，不发送“生成一面有功能的镜子”来替代系统开发。

## 6. 服务端与任务状态

客户端只能访问项目端点。项目服务端进行凭据管理、schema 校验、请求限流、预算检查、幂等登记、供应商调用、状态查询和结果登记。供应商密钥不得进入前端构建、浏览器日志或 Git。

资产任务使用持久 ledger：projectTaskId、idempotencyKey、inputRevision、recipeHash、providerVersion、providerTaskId、status、attempt、成本记录与产物摘要。幂等键基于确认请求和 recipe 版本，不把 runId 当唯一去重依据。

状态流为 reserved → submitting → queued／running → downloaded → validating → ready；另有 submissionUnknown、failed、rejected、timedOut。供应商“成功”最多代表可开始下载，项目 ready 必须完成文件与能力校验。

创建前先持久登记幂等记录并加锁；同键并发请求只创建一个任务。若提交超时且未取得供应商任务 ID，进入 submissionUnknown：优先按供应商支持的查询／幂等方式核对；没有核对能力时停止自动重建，使用占位并保留诊断，不把网络超时当作未收费。

查询使用有界退避，达到项目等待预算后停止前台等待。用户切换占位、重开或离开页面不等于供应商任务已经取消；只有收到取消确认才记为取消成功。后台是否继续查询由任务策略控制，已完成资源可进入缓存。

## 7. 缓存、文件与绑定

解释缓存键包含规范化输入、locale、提示词版本、模型配置版本和目录版本。确认记录保存具体结果，不依赖之后命中同一缓存。资产缓存键包含规范化 recipe、风格、生成版本与参数、后处理版本；敏感原句不得成为公开文件名。

优先使用本项目已验证资产；多用户部署时确认解释按会话隔离，不跨用户公开个人输入。供应商临时下载地址只用于服务端获取，不作为永久游戏路径。

下载限制来源、重定向、大小与超时；文件进入隔离验证区，再检查真实格式、外链资源、网格、纹理、尺寸、朝向、材质与所需动画能力。拒绝不受信任的外部 URI，防止加载时发生额外网络访问。通过后分配 assetId、内容摘要与稳定资源地址。

资产绑定独立于剧本状态：替换不改变 objectId、碰撞规则或观察事实。运行中尚未激活的实例也只有在新资源包围盒与性能验证通过后才可绑定；无安全边界时留到下一局。释放 GPU 对象不删除磁盘缓存，房间卸载不取消其他实例共享资源。

## 8. 界面、等待与失败

| 状态 | 玩家看到的反馈 | 游戏处理 |
|---|---|---|
| 解释中 | 正在理解输入，可返回修改 | 不锁死页面；旧 revision 结果不能覆盖新输入 |
| 有歧义 | 简短解释与具体选择 | 确认后才规划，不自动猜测 |
| 固定映射回退 | 明确标示使用预设解释 | 允许接受或修改，不称为实时 AI 生成 |
| 资产生成中 | 资源准备阶段、继续等待／使用占位 | 不显示虚构完成百分比或固定时间承诺 |
| 文件已到但不适配 | 使用可用素材，生成结果未通过适配 | 剧情保持完整，不用坏模型顶替 |
| 超时／服务不可用 | 可重试解释或用已支持方案开始 | 重试查询已有任务，禁止盲目重复付费创建 |

确认解释和等待阶段不计入约十分钟的实际游戏体验统计；另记录准备耗时。占位开始后暂停菜单可显示本局资产来源状态，不让下载进度持续干扰恐怖场面。

## 9. 预算与选择供应商

首批正常路径每个确认 revision 一次解释调用，最多一次纠错；每局最多两项资产生成任务。模型输出长度、并发数、单会话费用、每日费用及等待预算均由服务端配置执行，客户端不能提高上限。达到预算上限后停止新任务，保留已有查询与占位流程。

LLM 供应商和具体模型在接入时按中文语义、结构遵循、延迟、成本和账户可用性选择；本文不指定尚未验证的模型名。3D 接入以项目计划中的 Tripo 为目标，但实际 API 版本、可用模型、取消／幂等能力、价格与账户额度须按接入时官方文档核实并锁定。本文没有填写供应商端点或声称其支持项目所需全部能力。

单资产约 20,000 面是已有制作规则中的起始测试预算；纹理、内存与加载限额需在目标设备上测量。预算按生成资产与已有场景总开销联合计算，不能单项都合格而整局超预算。

## 10. 验证与接入顺序

1. 用固定输入实现同一内部协议：猫、花、音乐、歧义、空输入、不支持输入及玩家修正。
2. 接入一次真实解释请求，检查结构合法率、素材适配、错误回退和无效指令隔离；不得把模型自报置信度当质量证据。
3. 接入一个简单静态资产任务，验证提交、查询、超时、恢复、下载、校验、缓存与材质尺度。
4. 为 CAT01 等完整状态剧本验证资产能力；不适配时保留制作资产，记录失败原因。
5. 最后打开每局多项任务及完整流程，测准备时长、成本、帧率、错误率和占位使用比例。

必须测试并发重复提交、提交响应丢失、浏览器刷新、修改输入后的旧响应、假醒／死亡不重建任务、外链资源拒绝、产物不适配和账户额度不足。记录模型／提示词／schema／内容版本、任务标识、实际用量与错误码；默认不记录完整个人原句或密钥。

验收证据分为解释正确、规划合法、文件可用、表现适配、实际体验五层。任何一层失败都不能用“模型调用成功”代替完成结论。协议与任务测试可自动化；中文理解、视觉效果、旁白适配和恐怖体验需要人工核对。
